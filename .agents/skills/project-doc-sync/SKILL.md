# 项目文档同步

目标：让读者从概述找到入口，从手册完成操作，从模块说明理解实现。更新实际受影响的文档，保留已有有效内容，并明确区分当前行为、设计意图和历史实验结果。

## 确定范围与事实依据

- 先读仓库及受影响模块的 `AGENTS.md`、相关 README 和 `docs/README.md`；路径以当前仓库为准，不绑定本机绝对路径。
- 用户指定模块、文件或提交范围时按该范围工作。要求“同步最近改动”时先检查 `git status`、暂存区和未暂存 diff，再按需要阅读最近提交；没有明确基准时说明实际检查的范围，不把最近一次提交默认为全部改动。
- 要求全项目整理时，用 `rg --files` 盘点项目维护的 README 与文档，排除依赖、构建产物、缓存和第三方文件；索引本来就简洁且准确的，不必为了统一样式修改。
- 以当前工作区中实际生效的代码、配置、迁移和脚本为事实来源，包括未提交的新文件。diff 用于定位，必须阅读相关实现上下文，不能仅凭提交说明、旧文档或类名推断行为。
- 不把“代码已实现”写成“已部署”“验证通过”或“实验完成”；测试代码说明覆盖意图，实际测试结果才说明此次验证情况。计划中的能力不能写成现有能力。

## 核对调用链

按变更类型选择相关证据，不要求每次扫描全部模块：

| 变更 | 核对位置 |
| --- | --- |
| API、字段、鉴权 | 后端 Controller、DTO/VO、Security 配置、Service，以及前端 API 和实际调用方；推荐接口同时核对 Python schemas 与 Java 调用方 |
| 页面、路由、登录态 | 前端 router、store、请求拦截器、页面及相关后端权限校验 |
| 数据与业务规则 | Service、Mapper/XML、实体、Flyway 迁移、Redis/Neo4j 操作及相关测试 |
| 启动、配置、依赖 | application 配置及 profile、启动脚本、Compose、环境示例、pom、package.json、environment.yml |
| 异步、缓存、可靠性 | 事务边界、任务生成与消费、重试/幂等/依赖关系、配置开关、指标与故障测试 |

记录需要修正的事实及依据，例如“文档说必须改代理文件，但 Vite 已读取环境变量”。代码和文档冲突时先确认上下文与配置覆盖顺序；仍不能确定的点明确标注，不编造默认值或恢复步骤。此任务默认修改文档，发现业务缺陷时报告，不顺便改代码来迎合文档。

## 按文档定位分配内容

| 文档 | 保留内容 | 详细内容去向 |
| --- | --- | --- |
| 根 README | 项目目标、核心功能、服务关系、最短启动入口、文档导航 | 系统操作手册或服务手册 |
| 服务 README | 模块职责、主要技术与目录、启动前提、最短启动命令、常用验证命令 | 服务手册或模块说明 |
| 目录 README | 目录用途、文件索引、必要使用边界 | 相应工具或实验手册 |
| `docs/OPERATION_MANUAL.md` | 跨服务环境、启动顺序、配置、数据库迁移、完整联调和恢复操作 | 服务专属细节可链接服务手册 |
| `docs/*_GUIDE.md` | 服务开发与联调步骤、接口契约、字段示例、构建与排障 | 复杂实现机制链接模块说明 |
| `docs/*-module.md` 等模块说明 | 实现流程、关键类、数据模型、业务规则、事务与边界 | 环境配置和恢复步骤链接手册 |
| 实验方案与结果 | 假设、负载、步骤、断言、执行环境和历史结论 | 通用操作放实验手册，入口放实验 README |

- 上表是归属判断依据，不要求新建每一种文档，也不设硬性行数。优先更新已有权威位置，避免制造相互重复的手册。
- README 中能影响启动与使用判断的前提要留下，例如必填配置、依赖服务和集成测试需要 Docker；长配置表、逐接口字段、重试参数和恢复 SQL 移到手册。
- 不在 `License` 后追加功能实现章节。已有细节迁移后，用一句能力说明或有意义的链接替代。
- 新建或实质更新模块实现文档时，若仓库仍提供 `module-doc-writer`，读取并使用它的结构；不为单纯搬迁操作步骤强行创建模块说明。
- 历史实验报告保留当时的代码版本、数据与结论。若实现已变化，可更新实验索引或添加适用版本说明，不能改写历史结果以假装匹配当前代码。
- `docs/study-notes` 是按用户明确请求归档的学习记录。普通文档同步不新增或重写笔记；发现过时点时报告，明确要求同步笔记时再处理。

## 编辑与迁移

- 迁移前确认目标文档是否已经覆盖同一内容；合并缺失信息，减少重复事实。参数默认值等易变信息优先维护一处，概述使用链接。
- 保留关键限制、前置条件、执行目录、失败行为和恢复语义，不因精简而丢失操作所需信息。
- 文件或章节迁移时更新相对链接、代码路径、锚点和反向引用；命令的工作目录与文档所在目录不是一回事，必须明确命令从哪里执行。
- 新增文档后更新对应 README 和文档索引；沿用仓库现有命名和中文写作习惯。
- 保留工作区已有修改，不回退无关内容；整理文档不自动提交、部署、运行迁移或重放任务。

## 验证与交付

- 检查 diff，确认只有预期文档变化，迁出的独有信息有去向，代码示例和围栏完整。避免用简单标题正则拆分文档时误切代码块里的 Markdown 标题。
- 检查改动文档的本地文件链接和章节锚点；移动或重命名时搜索全仓引用。全项目整理时扩大到项目维护的文档。外部链接不必全部联网验证，但引用外部行为时应按任务需要核实权威来源。
- 执行 `git diff --check`，并单独检查未跟踪的新文档，因为它们不在普通 diff 中。
- 纯文档重组不必运行整套业务测试；命令与行为说明优先静态核对脚本和配置。只有实际执行过的命令才能报告“运行验证通过”，未做的运行验证说明范围即可。
- 最终简要列出调整的文档层级、主要修正、关键证据文件与验证结果；有未确认事实时列明。不报告未经检查的全项目一致性保证。

## 调用示例

- “使用 $project-doc-sync，根据当前未提交改动同步相关文档。”
- “使用 $project-doc-sync，检查整个项目的 README、手册与代码是否一致，并整理内容归属。”
- “使用 $project-doc-sync，只更新推荐服务相关文档，保留历史实验结果。”
